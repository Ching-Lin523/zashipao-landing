## 資料會怎麼處理

以下依本機 migration 推論，操作前必須用實際資料庫核對。指的是永久刪除 Auth 使用者；不能把軟刪除當作相同效果。

| 資料 | 目前結構的效果 | 處理注意事項 |
| --- | --- | --- |
| Email、登入資料、暱稱 | Auth 使用者刪除時處理 | 需使用 Supabase 支援的管理功能，不直接手寫 DELETE auth.users |
| tasks | user_id 外鍵 ON DELETE CASCADE | 私人待辦刪除 |
| bookings | user_id 外鍵 ON DELETE CASCADE | 所有預約刪除，包含歷史；共享場次本身不刪除 |
| booking_tasks | 預約／待辦外鍵連帶刪除 | 場次待辦關聯刪除 |
| session_results | 使用者／預約外鍵連帶刪除 | 個人場次成果刪除 |
| session_result_tasks | 成果外鍵連帶刪除 | 當場待辦快照刪除；平時快照不隨原待辦更動，不代表刪帳號仍保留 |
| room_presence | 使用者外鍵連帶刪除 | 資料庫的在線紀錄刪除，不等於 LiveKit 已斷線 |
| booking_events | user_id 設為 NULL，事件仍留存 | booking_id、場次名稱與時間仍在，不可稱為完整匿名化或全部刪除 |
| sessions | 不因刪除某位使用者而刪除 | 不影響其他使用者的場次 |
| LiveKit 在線參與者 | 不受 Supabase 外鍵控制 | 需另外確認本人已離房／移除本人，不能刪掉其他人在用的整間房 |
| 行事曆、使用者裝置資料 | 不受伺服器刪帳號控制 | 使用者自行移除已加入的行程；另檢查舊版 localStorage 與登入快取 |
| 服務日誌、備份、外部客服資料 | 不屬於上述資料表的連帶刪除 | 需依實際服務設定另行盤點，不能承諾即時抹除 |

## 管理者操作順序

### 1 收到申請並核實本人

請申請人寄信至 steph4mat@gmail.com 提出要求。驗證其控制帳號所使用的信箱，例如向系統登記信箱發確認信並取得回覆；不能只憑他提供一個信箱或 UUID 就刪除。不索取密碼、驗證碼或 Secret。

告知會失去待辦、預約與歷史成果，不能復原；如有需要，讓本人先保存想留下的內容。本人明確確認後，才安排實際刪除。

### 2 核對環境與影響範圍

確認操作的 Supabase 專案與本人 UUID。執行 `supabase/checks/account-deletion-audit.sql`，只查詢數量與外鍵；不要把查詢結果公開貼上 GitHub。

同時檢查是否新增了未列入本文件的資料表、Storage 物件、付款或第三方整合。SQL 只涵蓋已知表，不是完整資料探索工具。若使用者擁有 Storage 物件，先依實際服務規則處理，否則刪帳號可能失敗。

### 3 先處理剩餘預約與視訊

請本人離開所有視訊房間並停止操作。尚未開始的預約可由本人從網站取消，確認釋出名額；若有進行中場次，先結束個人參與。無法由本人操作時，交由具權限的管理者針對本人處理。

LiveKit identity 使用 auth user UUID，房名是 session-場次UUID。管理者若需移除參與者，核對這兩個值，只移除本人，不關閉整間共享房間。

刪除後再次查視訊：既有連線不會因刪 Auth 使用者自動中斷，也要考慮刪除前剛簽發的短效 token。現有 join token 最長 60 秒，但到期不等於既有連線會斷開；需在超過此期間後再確認本人沒有重進或殘留連線。任何一步失敗都標為待處理，不宣布全部完成。

### 4 先決定操作紀錄保留方式，再刪帳號

booking_events 目前在帳號刪除後保留事件，只把 user_id 清空。若決定刪除此人的事件，必須在 user_id 清空前完成範圍識別及授權處理；不要事後用 user_id IS NULL 批次刪除，會影響其他人的資料。

這一批不提供破壞性 SQL。事件保留政策尚待決定；正式受理前先確定並寫進對外說明。直接刪除 Auth 使用者不會自動產生每筆預約的 cancelled 操作事件。

使用 Supabase Authentication 的使用者管理功能或可信任後端 Admin API 執行永久刪除。由有權限的管理者操作，不新增前端管理金鑰。記錄操作是否成功；失敗時停止並查原因，不反覆刪其他資料碰碰運氣。

### 5 刪除後驗證

- 同一 UUID 再跑盤點：帳號應不存在，已知私人資料數量應為 0。
- booking_events 應符合已決定政策；user_id 計數變 0 不能證明事件消失，因為也可能只是變 NULL。
- 確認 LiveKit 本人不再連線，其他參與者仍可使用。
- 以專用測試帳號驗證原密碼不能登入、舊分頁不能讀寫原資料；同信箱重新註冊不代表恢復原帳號。
- 確認其他帳號的待辦／預約／成果沒有改動，空出的名額正確。
- 請本人移除自己的行事曆行程，並登出／清理本站裝置資料。伺服器無法抹去已下載的副本或截圖。
- 依日誌／備份政策記錄尚未到期清除的範圍。不要把「主資料已刪除」寫成「所有地方都立即刪除」。

Supabase 的舊 JWT 在到期前可能仍有效，因此不可以只看登入畫面或僅靠登出判定權限已失效。需測舊分頁與資料存取；若發現可繼續讀寫，先補強再對外開放。

### 6 回覆並留下最小必要紀錄

用私密管道回覆處理範圍與結果。內部只保留必要的案件編號、確認／完成時間、操作人、驗證結果與未完成項目；識別資料的保存期限需事先決定。不要把信箱、UUID 或私人待辦寫進公開 repository。

「如需刪除雜事房帳號，請透過我們的客服管道提出申請。我們會先確認申請由帳號本人提出，再協助處理。刪除後將無法使用原帳號，私人待辦、預約與場次成果也會移除。請先保存想保留的內容；已加入個人行事曆的行程需自行刪除。操作紀錄、備份及服務日誌的處理範圍與期限，會依公布的資料處理說明告知。」

目前不要刊登含未填客服地址或未決定期限的版本。

## 專用測試帳號驗收

準備可刪除的測試帳號 A 與對照帳號 B。A 建立待辦、未來預約、已完成場次與成果，並確認操作紀錄存在；B 保留自己的資料。記錄各表數量，不複製真實使用者的私人資料。

依以上流程只刪 A，核對私人資料、事件保留、名額、舊登入狀態與 LiveKit；B 的資料及視訊不受影響。測試需要明確指定可刪除的測試帳號後才進行。本次尚未執行。

## 技術依據

- 本專案 `supabase/migrations/`：tasks、bookings、room_presence、session_results、booking_events 的外鍵及觸發器。
- `app/api/video/route.ts`：getUser 驗證、LiveKit identity、token 有效時間與移除參與者。
- [Supabase 使用者資料管理](https://supabase.com/docs/guides/auth/managing-user-data)：刪除使用者、Storage 限制與 JWT 存續。
- [Supabase Admin deleteUser](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser)：永久／軟刪除差異；管理權限只能在可信任環境使用。
