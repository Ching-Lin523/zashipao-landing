# 場次管理 第一版操作指南

更新日期：2026/10/31。已檢查本機程式，未操作雲端資料。網站目前沒有獨立管理員頁面；先使用 Supabase 的 Table Editor 管理草稿場次，不需要每次寫 SQL。

## 建議現在使用的方式

由有 Supabase 專案權限的人登入 Dashboard → Table Editor → public.sessions。這是管理資料表，不是一般使用者網站；不要把專案管理權限發給試用者。

Supabase 官方支援透過 Table Editor 新增及編輯資料列：[資料庫說明](https://supabase.com/docs/guides/database/overview)。畫面按鈕名稱可能隨介面版本調整。

## 新增一場

1. 確認專案正確，選擇 public.sessions，使用新增資料列（Insert row）。
2. 填以下欄位，先保持 is_published = false，儲存為草稿。
3. 檢查日期、台灣時間、容量與名稱，確認開始時間仍在未來。
4. 確認後才把 is_published 改為 true；儲存即會影響連到同一資料庫的網站，並不需要 GitHub 合併或 Vercel 重新部署。
5. 到網站的「可預約場次」重新整理，核對顯示內容。

| 欄位 | 白話意思 | 填法 |
| --- | --- | --- |
| id | 場次識別碼 | 若現有欄位已設定自動產生 UUID，保留預設；不要手動複製另一場的 id |
| title | 場次名稱 | 例如「午間雜事衝刺」 |
| starts_at | 開始時間 | 日期、時間及時區一起填，見下方例子 |
| ends_at | 結束時間 | 必須晚於開始時間 |
| capacity | 人數上限 | 目前產品採 1–5 人；一般填 5，實際資料庫限制待核對 |
| is_published | 是否公開 | false 草稿；true 公開 |
| created_at | 建立時間 | 若已有 now() 預設，保留預設 |

public.sessions 原始建表 SQL 沒有收在目前 migrations 裡；上述預設及容量限制依原有畫面與產品設定，請先用唯讀盤點核對，不能假設新資料庫已具備。

## 時間怎麼填

範例：2026/12/02 台灣時間 12:00–12:50。

- starts_at：`2026-12-02T12:00:00+08:00`
- ends_at：`2026-12-02T12:50:00+08:00`

`+08:00` 表示台灣時間。若表格以 UTC 顯示，上述時間可能顯示為 04:00–04:50 +00，代表同一時刻。若編輯器使用時間選擇器，先確認它顯示的時區；不要在不確定時區時只填「12:00」。儲存後到網站確認，網站固定以 Asia/Taipei 顯示。

範例日期不是每次都有效；實際操作時請選尚未開始的日期。週三、週四、週五各兩場可逐列新增，沒有每週自動重複排程。

## 修改與下架的界線

| 情境 | 第一版建議操作 |
| --- | --- |
| 尚未公開、沒有預約的草稿 | 可編輯名稱、時間、容量 |
| 已公開但要修改 | 先確認沒有預約，也沒有進行中房間；收回為草稿再修改，確認後重新公開 |
| 已有人預約 | 不直接改日期、時間或下架，先處理通知與預約安排 |
| 想暫停新預約，但讓已預約者照常進房 | 現在沒有獨立開關，不能用 is_published 取代 |
| 已經開始或結束 | 不用改時間來延長或重開舊場，另外新增場次 |
| 想刪除舊場次 | 不直接刪除，可能有預約／成果外鍵及保留需求 |

Table Editor 不會替你執行完整的管理規則。公開場次可能在你查看「0 人」後又有人預約；因此「剛看過沒人」不能當作修改時一定無人。對外開放後，涉及既有公開場次的修改應由具交易鎖定與重新驗證的管理功能處理；人工操作優先只編輯未公開草稿。

## 為什麼不能把公開開關當停止預約

目前 list_available_sessions 只列公開且未開始的場次；等候區、房間及在線資格也檢查 is_published。因此設為 false 會同時影響既有預約者的使用資格，不只是從列表隱藏。

改期也有其他影響：使用者的行事曆不會自動更新，既有預約的時間衝突不會因管理者改期自動重新檢查，已建立的 LiveKit 房間 metadata 可能仍保留原結束時間。網站尚無管理者改期／取消通知流程。

## 可先做的驗收

以未公開的測試場次新增一列，檢查時間與欄位；公開後確認網站顯示正確。若已被預約，停止把它當作可任意修改的草稿。

這份文件沒有替你新增或改動任何場次。唯讀盤點檔為 `supabase/checks/session-management-audit.sql`，第一次可執行確認結構及場次數量；日常新增草稿可使用表格，不需要一直貼 SQL。

## 下一版獨立管理頁面的需求

若 Table Editor 對兩位仍不方便，再做網站內管理頁；建議只先支援新增草稿、列表與發布。

- 管理員身份由可信任的後端設定，不用公開可編輯的暱稱／user_metadata 判定，不在前端藏一個按鈕就當授權。
- API／資料庫每次檢查管理員權限，預設拒絕一般使用者；不用讓所有登入帳號都能改 sessions。
- 顯示台灣時間，驗證未來時間、結束晚於開始及容量 1–5。
- 修改時鎖定場次並重新確認預約人數、場次狀態，避免與預約競爭。
- 分開設計公開、停止接受新預約、取消場次；不要讓已預約者莫名無法進房。
- 有預約的改期、取消、通知、成果與 LiveKit 處理另做完整流程。
- 保留必要管理紀錄，測試非管理員無法新增／修改／發布。
